# Initiative review rules

Inputs: read the feasibility file at `{FEASIBILITY_PATH}` — the technical feasibility analysis; the review's Feasibility section and its `feasibility` frontmatter field come from it. Read the alignment file at `{ALIGNMENT_PATH}` if it exists. If missing, alignment was not assessed (no RHAISTRAT parent or agent did not complete).

Determine recommendation:
- submit: Initiative passes (7+ with no zeros)
- revise: Initiative fails but can be improved
- split: right_sized scored 0, indicating the initiative is a grab-bag of genuinely separate initiatives — each serving a different goal and ownable by a different, unrelated team or group, not facets of one mission. BUT only if no OTHER criterion scored 0 — splitting an initiative with an unfixable problem just produces more initiatives with the same problem. Otherwise **recommend revise**.
- reject: 3+ criteria scored 0, fundamentally infeasible, or needs rethinking

Do NOT recommend split for a single overarching goal owned by one team or related group of teams (however many facets, problems, or domains it spans), for connected pieces under one theme, for individually-minor items in a deliberate container, or for **delivery-coupled** workstreams (must ship together or share a critical path) — recommend revise instead. Breadth across domains or personas is not, by itself, grounds to split.

Set `needs_attention=true` when the Initiative needs human review despite its score — e.g., feasibility is indeterminate/infeasible, references non-existent components, or has concerns the rubric doesn't capture. When true, also set `needs_attention_reason` to a concise explanation (1-2 sentences) of what needs human attention. When false, set `needs_attention_reason=null`. The flag follows what the review itself records: a concern you write anywhere in the review that the scores do not reflect — a title that does not describe the body, a draft note left in the text ("confirm before submission"), a component that does not exist in the platform — sets `needs_attention=true` with that concern as the reason and its source recorded by the next paragraph; a review that names something as needing correction and sets the flag false contradicts itself.

Whenever you set `needs_attention=true`, also record where the flag comes from: `needs_attention_source` is `feasibility` (a concern from the feasibility file), `alignment` (a concern from the alignment file, including a `weak` verdict), `rubric` (a concern about a rubric criterion) `classification` (the item reads as another registered type, below) or `agent` (anything else); when the source is `feasibility` or `rubric`, set `needs_attention_dimension` to the score field the concern is about (`what`, `why`, `scope`, `open_to_how` or `right_sized`) — a feasibility note that the Initiative prescribes its implementation or technology stack is about `open_to_how`. Leave both fields unset when `needs_attention=false`. When several concerns apply at once, record the source that cannot be cleared automatically: a `weak` alignment verdict is always `alignment`; otherwise `classification` first when it applies (its reason carries the filing advice), then `alignment`, `rubric` or `agent`, all of which take precedence over `feasibility` (only a `feasibility` flag is ever cleared after a revision).

A misfiled item (design §6 stage 2): when the task text reads as one of the other types in the classification digest the agent prompt names — that type's signals match the text and this type's counter-signals do — it is likely that type at the wrong door, whatever the scores say (one customer-facing capability with acceptance criteria, one customer's request or escalation, a need that fits one release, rather than a body of work a team commits to). Judge the substance of the text, not its shape: every task file here follows the Initiative template, so an objective, a problem statement, scope boundaries and acceptance criteria are the template's doing and no evidence either way; what counts is the teams, the time span and the distinct deliverables the text actually names — one team, one release and one capability is an RFE however its sections are titled. Flag it with `needs_attention_source=classification` and a reason built from the matching description, `likely a <its entity>: <evidence>; consider /rfe-create --type <its type>` (for the RFE description: `likely an RFE: <evidence>; consider /rfe-create --type rfe`). When the alignment verdict is `weak` as well, the source stays `alignment` and `needs_attention_reason` carries both: the alignment explanation first, then `; ` and the complete classification sentence (`likely a <its entity>: …; consider /rfe-create --type <its type>`), so the misfiling survives the reassess cycle. Keep the scores and the recommendation as they are; the review neither relabels nor moves the item.

In a reassessment after a revision (First pass is false), a feasibility note about prescriptive implementation detail counts as addressed when the reassessed `open_to_how` scores 2 and the removed-context record (`<ID>-removed-context.yaml` next to the task file) shows the content was removed; do not raise `needs_attention` for it.

Parse the alignment verdict from the alignment file's `**Alignment**:` line. If the alignment file was missing or alignment is `not_assessed`, omit the alignment field — it defaults to `not_assessed`.

If alignment is `weak`, set `needs_attention=true` (strategic misalignment requires human review).
